## 0. RESOLUTION (2026-08-02) — read this before the rest

The "latent, layout-sensitive PD-stack bug" described in the sections below **was not a
firmware bug at all — it was a build-system artifact.** The `Firmware/Makefile` did not
track header dependencies, so editing any header (notably `pdsink/src/pd/utils/afsm.h`)
left stale `.o` files and produced an inconsistent binary that crashed on boot. That fully
explains the "any no-op line unmasks it", the contradictory bisects, and the phantom
"afsm dispatch-pointer corruption" (a clean-charger + external-3.3 V debug session traced
the phantom write to `set_states` legitimately storing a RAM-resident interceptor table).

Fixes:
- `Makefile` now uses `-MMD -MP` + `-include *.d` (commit `d63c723`) so header edits
  rebuild dependents. **`make clean` is the safe fallback if a stale build is ever suspected.**
- The mid-hunt `afsm` dispatch guard was a **false positive** (interceptor_table is
  legitimately in RAM, a runtime-initialized static) and was reverted (`86d333a`).

**A clean rebuild of the real fix batch (`92cf4a9`..`494a118`) boots and passes the full
standalone self-test 53/53 on hardware** (all voltages incl. 28 V EPR, PPS, AVS; EPR entry;
measurements; output; protection; stream). PD/EPR negotiation works. The bounds-guard fixes
(source_caps clamp, timer/resize guards) remain as valid defense-in-depth. The charger-hang
analysis in §5b/§6 stands as a separate, real hardening topic. Sections 1–6 below are the
original hunt notes, retained for history.

## 2. The bug that blocked shipping

Flashed the new firmware → **fault-loops on boot** (no USB enumeration).
Systematic debugging established:

- **Deterministic HardFault**, not a charger/VBUS collapse: CFSR=`0x101` (IACCVIOL+IBUSERR),
  HFSR forced, PC = a **garbage address that varies per run** → a call through a corrupted
  function pointer. Stacked frame IPSR=15 → fault context is `SysTick_Handler →
  axxpd_tick_pd() → pd::Task::set_event → afsm dispatch`.
- afsm dispatches via `enter_table[state_id](impl())` / `run_table[state_id](impl())`
  (`afsm.h:246,264`) — arrays of function pointers, **no bounds check on a corrupted table
  pointer**. So a wild write onto an fsm object's first 16 bytes → garbage call.
- **ETL bounds-checks are compiled OUT** (`Makefile` C_DEFS has no `ETL_CHECK_PUSH_POP`;
  `ETL_ASSERT` expands to nothing). Any fixed-buffer overflow silently corrupts adjacent RAM.

### Root cause (code-review conclusion)
Highest-probability trigger = **`source_caps` push_back overflow** (`pe.cpp:244`):
`etl::vector<uint32_t, 11>`, filled from a received `Source_Capabilities`/EPR caps message.
`rx_emsg` is a 260-byte buffer → `size_to_pdo_count()` can reach ~65; without a clamp the
loop pushes far past 11, overrunning `source_caps` (a `Port` member) into adjacent
state / one object over into FSM dispatch pointers. **This matches the field symptom
"sometimes I must restart the USB charger and then it works"** — a bad charger state emits
the triggering message. Fixed by the clamp in `606f331` (`pe.cpp:243`).

### Important caveat about the "layout-sensitive" reading
Mid-debug I concluded "*any* code change, even one no-op line, unmasks a latent bug." That
was likely **confounded**: over ~30 flash/reset cycles the Anker charger degraded into a
bad PD state, and by the end even the **pristine baseline HardFaulted** on boot. So the
late fault-loops (including the "baseline + 1 noop line" test) were probably the *bad
charger* overflowing `source_caps`, not a layout effect. This must be **re-tested on a
clean charger** to confirm the fix set actually resolves it.

## 5b. Why a firmware crash can hang the charger (CC / dead-battery hand-off)

Corrected understanding (per the TPD4S480 datasheet §6.3.3 / §7.2.2.2 and `AxxPD_dev/AxxPD_design.md`):

The **CC Rd termination is MCU-owned in normal operation**, NOT provided by the TPD4S480.
Sequence: unpowered → the TPD4S480's own dead-battery Rd wakes the source (5 V on VBUS) →
once powered, the TPD4S480 closes its CC OVP pass-FETs (~3.5 ms) and **removes its own
dead-battery Rd within ~5.7–9.5 ms**, so the PD controller's Rd is fully exposed. From then
on the Rd is the STM32 UCPD: the DBCC dead-battery pulldowns (PA9/PA10, active whenever
VDD > ~1 V) at reset, then the normal UCPD Rd (PB6/PB4) after
`HAL_PWREx_DisableUCPDDeadBattery()`. The TPD4S480 is only a protection pass-through after
hand-off.

Consequence: a firmware fault can strand the source at **two** layers:
- **PD layer:** the sink goes silent (no GoodCRC / no responses; this stack sends GoodCRC in
  software, so a crash stops ACKs). The source retries → SoftReset → HardReset → and after
  repeated failures many chargers enter a protective latched state needing a power-cycle.
- **Type-C layer:** because we own the Rd, a reset/brownout perturbs the CC termination too —
  the known ~6 ms double-parallel-Rd (2.55 kΩ) hand-off glitch on reset, and, in the worst
  case, if VDD dips below the DBCC threshold (real brownout, with the TPD4S480 Rd already
  released) the **Rd disappears entirely → the source sees a hard detach.** This is the
  mechanism behind the documented 28 V/EPR "VBUS collapse → BOR → reboot" loops.

The firmware never *tries* to hang the charger; but owning the CC Rd means a crash disturbs
both the PD link and the Type-C attach. A 3rd-party charger latching after that is its own
protection — we can only avoid provoking it (don't fault; fail safe fast, keep VDD up, reset
cleanly, re-assert Rd quickly). See §6 for the full mitigation design.

## 6. How to never hang the charger (investigation, 2026-08-01)

Two firmware audits (fault-recovery/CC-continuity, and PD-link robustness) plus the
TPD4S480 datasheet drove this. Key mechanism recap: **a charger hangs when the sink goes
silent** (no GoodCRC → retries → SoftReset → HardReset → protective latch needing a
power-cycle) **or when the CC Rd glitches/detaches**.

Crucial facts established:
- **GoodCRC is software**, emitted in the UCPD ISR (NVIC prio 0) — `ucpd_driver.cpp:539-570`.
  The STM32G4 UCPD has **no hardware auto-GoodCRC** (`get_hw_features`, `:450-468`).
- GoodCRC therefore **survives a stalled/slow app** (main-loop stall, FSM deadlock) — the
  ISR keeps ACKing. It does **NOT survive a HardFault/lockup** — the fault stops the ISR too.
  ⇒ **A crash = silent sink = charger hang. Not crashing is the load-bearing defense.**
- SysTick ticks the PD stack every 2 ms independently of the main loop
  (`stm32g4xx_it.c:223-226`); long blocking ops (LCD DMA, INA I2C) tick PD via idle callbacks.
- On reset, `PWR.UCPD_DBDIS` auto-clears → **DBCC Rd re-asserts in hardware before code runs**;
  no open-CC window while VDD stays up.

There are two tiers of "never":

### Tier 1 — never *permanently* hang (kills the "restart the charger" symptom). Achievable in firmware.
- **A. Don't crash — DONE (confirm on clean charger).** The RX path is now fully
  bounds-checked: `source_caps` clamp (`pe.cpp:243`), timer-id guard (`timer_pack.h`),
  message resizes clamped (`data_objects.h`, `prl.cpp:267`), and `read16/read32/append_from`
  are internally bounded, SPSC queue masked. Audit found **no remaining unchecked RX write**.
  This removes the crash trigger → the ISR keeps ACKing → the charger never sees a silent sink.
- **A+. Detect corruption before it jumps — DONE (`2770eac`).** The afsm dispatch
  (`afsm.h` execute_enter/run/exit) now range-checks the state-machine table pointers
  (the fsm object's first 16 bytes — exactly what a wild write smashes) against flash
  `[0x08000000,0x08040000)` before dispatching. A corrupted table pointer → the
  `afsm_dispatch_fault()` hook (`main.c`) forces output off + clean reset instead of a
  garbage jump (or, worse, a jump into valid-but-wrong code that could mis-drive the
  output). False-positive-proof: valid dispatch pointers are ALWAYS in flash. This backstops
  *any* corruption — found or unfound — and also covers the boot window.
- **B. Fail safe fast if we ever do crash — DONE.** Fault handlers force output OFF +
  `NVIC_SystemReset` (`stm32g4xx_it.c`); double-fault → lockup → IWDG (5 s) catches. On reset
  DBCC holds the CC attach; reboot re-negotiates at 5 V via the **loop-breaker** (never restore
  EPR at boot, `main.c:702`) + abnormal-reboot autostart suppression (`main.c:435,580`). So a
  residual crash becomes a fast self-recovering glitch, not a permanent hang. **This is the
  single biggest change vs. baseline** (baseline spun forever in HardFault → permanent hang).
- **C. Close the boot watchdog gap — DEFERRED (documented, not implemented).** IWDG starts
  only at `main.c:599`, after boot negotiation, so a *non-faulting* hang during phase-1 has no
  watchdog. Deliberately NOT done blind: moving the IWDG start is boot-timing-fragile (MEMORY:
  early-boot changes have caused VBUS-cycle loops) and untestable with the charger latched, and
  its value is now largely covered by A+ (a corruption during boot is caught by the dispatch
  guard). If implemented later: start IWDG early with a generous timeout, refresh inside the
  phase-1 wait loop + boot selector, and **verify on hardware**. Also considered and skipped:
  a global `-DETL_CHECK_PUSH_POP` (redundant — the RX path is already fully bounds-checked, per
  audit; not worth a global untestable codegen change).

### Tier 2 — never even *briefly* glitch the charger, even during an MCU crash/reboot. Needs hardware.
- **D. (optional FW) Extend the ISR responder** to auto-emit `Accept` to an incoming SoftReset
  and self-request 5 V after a HardReset, in ISR context (the GoodCRC/cable-emu ISR-TX pattern
  proves it works). Hardens the *stalled/slow-app* case at the protocol level — but **cannot
  survive a HardFault** (same ISR dies). Medium effort, modest marginal benefit over A+B+C.
- **E. (hardware, next rev) The only true guarantee.** Because GoodCRC is inherently software
  on the STM32 UCPD, *any* MCU fault/reboot creates a ~150 ms–1 s ACK gap. To keep the
  charger ACKed through an MCU crash/reboot you need a **dedicated PD PHY/controller with
  autonomous GoodCRC + retry** (e.g. FUSB302, or a full autonomous controller like TPS26750).
  Also hardware: the **~1.2 s VBUS-off → VDD brownout → CC detach** case (charger hard-reset
  after an output short at ≥15 V) is unfixable in firmware — needs a lower OCP / active
  current-limit (eFuse) so we don't provoke the hard-reset, and it's the same board-rev item as
  the deferred short-circuit issue. Minor: raise the BOR option-byte level for a cleaner reset
  on a sagging rail.

### Bottom line
"Never permanently hang the charger" (i.e. eliminate the field *restart-the-charger*
annoyance) is achievable **in firmware** and is essentially done by A+B; add **C** to close the
last silent-hang path. A hard "never even glitch it, mid-crash" guarantee requires **E**
(autonomous-GoodCRC PD PHY) and is a next-rev decision. Recommended order: (1) confirm A on a
clean charger, (2) implement+test C, (3) consider D if stalled-app cases ever appear, (4)
evaluate E for a future revision.
