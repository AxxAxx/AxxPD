## 2. The bug that blocked shipping

Flashed the new firmware → **fault-loops on boot** (no USB enumeration).
Systematic debugging established:

- **Deterministic HardFault**, not a charger/VBUS collapse: CFSR=`0x101` (IACCVIOL+IBUSERR),
  HFSR forced, PC = a **garbage address that varies per run** → a call through a corrupted
  function pointer. Stacked frame IPSR=15 → fault context is `SysTick_Handler →
  axxpd_tick_pd() → pd::Task::set_event → afsm dispatch`.
- afsm dispatches via `enter_table[state_id](impl())` / `run_table[state_id](impl())`
  (`afsm.h:246,264`) — arrays of function pointers, **no bounds check on a corrupted table
  pointer**. So a wild write onto an fsm object's first 16 bytes → garbage call.
- **ETL bounds-checks are compiled OUT** (`Makefile` C_DEFS has no `ETL_CHECK_PUSH_POP`;
  `ETL_ASSERT` expands to nothing). Any fixed-buffer overflow silently corrupts adjacent RAM.

### Root cause (code-review conclusion)
Highest-probability trigger = **`source_caps` push_back overflow** (`pe.cpp:244`):
`etl::vector<uint32_t, 11>`, filled from a received `Source_Capabilities`/EPR caps message.
`rx_emsg` is a 260-byte buffer → `size_to_pdo_count()` can reach ~65; without a clamp the
loop pushes far past 11, overrunning `source_caps` (a `Port` member) into adjacent
state / one object over into FSM dispatch pointers. **This matches the field symptom
"sometimes I must restart the USB charger and then it works"** — a bad charger state emits
the triggering message. Fixed by the clamp in `606f331` (`pe.cpp:243`).

### Important caveat about the "layout-sensitive" reading
Mid-debug I concluded "*any* code change, even one no-op line, unmasks a latent bug." That
was likely **confounded**: over ~30 flash/reset cycles the Anker charger degraded into a
bad PD state, and by the end even the **pristine baseline HardFaulted** on boot. So the
late fault-loops (including the "baseline + 1 noop line" test) were probably the *bad
charger* overflowing `source_caps`, not a layout effect. This must be **re-tested on a
clean charger** to confirm the fix set actually resolves it.

## 5b. Why a firmware crash can hang the charger (CC / dead-battery hand-off)

Corrected understanding (per the TPD4S480 datasheet §6.3.3 / §7.2.2.2 and `AxxPD_dev/AxxPD_design.md`):

The **CC Rd termination is MCU-owned in normal operation**, NOT provided by the TPD4S480.
Sequence: unpowered → the TPD4S480's own dead-battery Rd wakes the source (5 V on VBUS) →
once powered, the TPD4S480 closes its CC OVP pass-FETs (~3.5 ms) and **removes its own
dead-battery Rd within ~5.7–9.5 ms**, so the PD controller's Rd is fully exposed. From then
on the Rd is the STM32 UCPD: the DBCC dead-battery pulldowns (PA9/PA10, active whenever
VDD > ~1 V) at reset, then the normal UCPD Rd (PB6/PB4) after
`HAL_PWREx_DisableUCPDDeadBattery()`. The TPD4S480 is only a protection pass-through after
hand-off.

Consequence: a firmware fault can strand the source at **two** layers:
- **PD layer:** the sink goes silent (no GoodCRC / no responses; this stack sends GoodCRC in
  software, so a crash stops ACKs). The source retries → SoftReset → HardReset → and after
  repeated failures many chargers enter a protective latched state needing a power-cycle.
- **Type-C layer:** because we own the Rd, a reset/brownout perturbs the CC termination too —
  the known ~6 ms double-parallel-Rd (2.55 kΩ) hand-off glitch on reset, and, in the worst
  case, if VDD dips below the DBCC threshold (real brownout, with the TPD4S480 Rd already
  released) the **Rd disappears entirely → the source sees a hard detach.** This is the
  mechanism behind the documented 28 V/EPR "VBUS collapse → BOR → reboot" loops.

The firmware never *tries* to hang the charger; but owning the CC Rd means a crash disturbs
both the PD link and the Type-C attach. A 3rd-party charger latching after that is its own
protection — we can only avoid provoking it (don't fault; fail safe fast, keep VDD up, reset
cleanly, re-assert Rd quickly). See §6 for the full mitigation design.
